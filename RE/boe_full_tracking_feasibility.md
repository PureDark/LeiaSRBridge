# BOE 完整双眼与头部姿态扩展可行性

日期：2026-10-21。范围：`BOE_3DET_SDK.dll` 公开168字节结果、其双眼三维计算、内部关键点/PnP，以及 `BoeLandmark.dll` 的输出。全程静态分析，没有开启摄像头、调用 MCU、运行游戏或修改0.2.0发行包。

## 结论

可以比当前 COM 五标量通道多取得很多信息。**原厂 SDK 已经分别计算两只眼的三维位置，内部甚至已有完整面部关键点和 PnP 旋转计算**；当前限制主要是 FaceTracking.exe -> COM 发布时丢弃这些字段，不是已经证明硬件只能输出一个点。

但必须区分：

- 两眼结果是分别由双相机对应点计算的三维位置，**不是中心点加减固定 IPD**。其二维定位点是每只眼16个眼睑轮廓点的平均，**不是虹膜/瞳孔中心，也不是视线方向**。
- SDK 内部确实计算三个姿态角，但没有通过168字节公开结构导出；目前只用于一个角的阈值判断。能截获计算结果，不代表已经得到坐标/精度经过验证的 Leia HeadPose。
- `BoeLandmark.dll` 当前路径生成468个二维面部关键点。没有找到耳廓定位或双耳三维估计；不能把太阳穴/脸轮廓点标成真实耳朵。
- 最小改动是保留官方 FaceTracking.exe 的相机采集与原厂算法，在私有 SDK 代理中截获完整结果并发布新 IPC。完整旋转需要额外截取内部9点或PnP结果，不能只扩展公开结构的读取长度。

## 双眼结果的确切数据链

1. `BoeLandmark.dll!BoeLandmark::doInfer` `0x1801BE770` 调 `0x1801BFA50`。后者两种输出名称分支都以 `k=0; k<5616; k+=12` 迭代，每次读取模型一个三float元素的前两个数、缩放为像素坐标、写入`vector<cv::Point2f>`。5616/12=468点。第三分量未导出到这个向量；不能把它当公制深度。
2. `BOE_3DET_SDK.dll` 两个worker `0x1800A50D0`、`0x1800A5240` 调上述导出，并为xy加回当前ROI起点。
3. `0x18009C2B0`从密集关键点构造每相机的两个眼周中心及姿态点。
4. `0x1800AFB70`取得两个相机的眼周中心，去畸变/校正，按双目视差分别计算中心、眼A、眼B三组XYZ，保留既有历史处理。三组最终写内部结果偏移60、72、84。
5. `0x18009CC80`成功分支 `0x18009F35A`至`0x18009F3F1`把三组传给`0x1800272D0`的a3/a4/a5；该函数写对象96/108/120。
6. `0x1800261B0`的`0x180026A31`至`0x180026A66`把三组逐float复制到公开结果0/12/24。

关键证据：`boefull-landmark-forward.txt`、`boefull-landmark-forward-key.txt`、`boefull-landmarks-arrange.txt`、`boefull-0x1800AFB70.txt`、`boefull-position-asm-key.txt`、`boefull-0x18009CC80.txt`、`boefull-0x1800272D0.txt`、`boefull-result-asm-key.txt`。

## 不只5点：内部密集点与旋转

`0x18009C2B0`保留全部468个`Point2f`于每相机结构+24；+48保存6个紧凑点（上述5点再加双眼中心），而公开结果只取前5。+72保存9个`Point2d`供PnP，顺序为密集点：

`4, 8, 152, 33, 133, 263, 362, 57, 287`。

这意味着现有公开结构不能无损重建内部9点；复制整个168字节仍不包含额外四个PnP点。第三点4位于鼻部拓扑，57/287为口部附近点；其准确训练语义/模板一致性必须连同模型验证，不能由常见468点命名直接推出测量精度。

`0x1800AFB70`末尾将两个相机的9点矢量交给`0x1800B3090`；后者两次调用`0x1800B24E0`。`0x1800B24E0`：

- 建立硬编码9点三维人脸模板。
- `0x1800B2761`调用`cv::solvePnP`，使用相机参数和点集，产生旋转向量及平移。
- 随后利用旋转向量转换得到三个角，写入a8/a9/a10（弧度）以及a5/a6/a7（度）；另输出一个3x3旋转矩阵。
- 这里的角并没有存入公开168字节结构。

`0x1800B3090`只平均两个相机的第二个度输出，按**-8/+8**阈值生成两个状态字节，写singleton对象+1328；其他角与矩阵在函数返回后丢弃。阈值经过原字节核对，不是只看反编译数字。即使获取这些角，也需单独确定轴、旋转顺序、手性、镜像与Leia屏幕坐标转换。这里尚未把某个变量强行命名为pitch/yaw/roll。

证据：`boefull-pose-xrefs.json`、`boefull-pnp-callers.json`、`boefull-pnp.txt`、`boefull-pose-pnp-asm-key.txt`、`boefull-pose-store.txt`、`boefull-pose-store-asm.json`。另一个Rodrigues调用`0x180039070`来自`setCameraMat_3D`，属于相机参数处理，不能拿其存在当额外头追输出。

原厂硬编码模板与选点顺序仍需专门验证。本次原PE解码模板已保存在`boefull-pe-constants.json`，其若干顺序与通常的468点解剖位置对应并不直观，因此没有把原厂内部PnP的输出直接认定为合格6DoF。应通过重投影误差、单轴转头与坐标标定再决定复用或改为自己的求解器。

## 双耳和视线的边界

本次恢复的468点接口、公开结果、PnP和三维输出未发现独立耳廓/耳孔定位。脸轮廓两侧点不是耳朵；按头部旋转和预设头宽推算的耳位置属于模型估计，也不是测得的真实双耳。若调用方只需估计耳位，可明确标为estimated并校准个体尺寸；若要求真实双耳测量，则需要有耳部关键点的模型、可见性/遮挡处理和双目重建。

同样，这个468点路径未加入MediaPipe478点拓扑中的虹膜环。现成眼位是眼睑几何中心，不能标成pupil/gaze，也不能凭它推断用户看的方向。

## 最小实施路线与失败语义

### 第一阶段：双眼，不重写采集

1. 保留官方FaceTracking.exe负责摄像头初始化、Media Foundation帧采集和当前SDK调用。
2. 在桥接私有目录放一个ABI相同的SDK代理，原厂SDK保留字节和哈希。代理仅转发导出，在`doEyeTrack_3D`调用返回后复制完整168字节到独立扩展IPC，不恢复已删除的滤波旁路。
3. 增加自身单调QPC观察时间、顺序号和结果有效位；按调用返回值与数值有限性/深度有效性判定。SDK自身时间不能标成曝光时间。中心与两眼必须来自同一次SDK调用，发布用seqlock/整包版本避免撕裂。
4. 新IPC字段由后台转发到Leia`Head`/`EyePair`；原有交织中心、+8mm补偿和40ms预测策略保持一致，补偿不能只作用于中心而忘记双眼，也不能双重叠加。
5. 用真实屏检查遮眼、左右眼身份、测得IPD范围、深度连续性和投影，才将双眼能力宣告可用。

这条路线无须改MCU标定，也不需要重写相机采集。对原厂SDK精确版本实施，代理转发与原厂文件身份需离线验证；读取能力的代理与先前无效的滤波旁路是不同功能。

### 第二阶段：旋转

最小实验可以在原厂`0x1800B24E0`返回时捕获a8/a9/a10或矩阵，以及对应帧/相机。优点是无需重复推理；缺点是依赖内部地址/ABI、原厂模板和姿态求解质量，并且原厂调用没有明确使用solvePnP返回布尔值作为完整可信度。

更可控的实现是截取原厂内部9点或BoeLandmark的468点结果，保存同帧相机参数，**自己的代码调用solvePnP/双目姿态拟合**：检查点序、重投影误差、失配、遮挡、单位/坐标变换和时间连续性。可以继续复用官方采集及关键点模型，完全不必从零训练眼追。仅有168字节内的5点可尝试简化5点PnP，但眼周均值与模板定义要一致，不能宣称等价于内部9点算法。

失败时发布`poseValid=false`，保留现有无脸回退显示策略；不把上帧角度加新时间当新观测，不把默认零旋转标成真实测量。有效双眼与有效旋转应有独立能力/有效位，某一路失败不应阻止已有3D显示。回退零角或保持角若为应用便利需要使用，必须区分其来源。

### 第三阶段：额外人体点

耳位、虹膜、视线各自需要新模型或额外算法，不能通过补齐字段得到真实观测。在第一/第二阶段验证前没有必要先替换为整个Leia追踪程序；是否可复用Leia模型/程序取决于其摄像头输入、硬件识别、标定、光照模式及接口，另行分析。
